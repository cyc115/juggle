# Juggle RCA — 2026-07-02

**Author:** researcher (thread BV), read-only investigation of `/Users/mikechen/github/juggle` @ `main` (HEAD `5380223`).
**Scope:** (1) catalogue the ~8-hour overnight-session incident log handed over verbatim by the orchestrator; (2) root-cause why coder task nodes run 20–40 min wall-clock. Part 1 facts are the orchestrator's observations (not re-derived); Part 2 findings are grounded in the repo (`config.json`, `juggle_task_templates.py`, `juggle_cmd_integrate.py`, `juggle_cmd_agents_worktree.py`, `Makefile`, `pyproject.toml`) and tonight's `git log` timings.

## Executive summary

The overnight autonomous run surfaced **11 catalogued issues**: 9 machinery defects (all fixed + merged tonight) and 2 recurring-but-expected infra-friction patterns. Three defects were SEVERE and shared one anti-pattern — **test isolation leaking into real production state** (spool dir, live `config.json`) — plus one class of **silent/blocking hazards in the watchdog tick** (idle-nudge false positive, orphan-guard race, respawn churn, a lock with no timeout that hung the tick for 10+ min). All nine have regression pins and merged commits. On latency: a typical coder task spends the **majority of its wall-clock running the full test suite, not writing code** — and critically, both the coder's self-verify and the `juggle integrate` gate run the suite **serially** (`uv run pytest -q`, ~330 s / 5.5 min), even though `make test` already supports `-n auto`. Running the full suite 2–3× serially per task (self-verify + integrate gate + rebase re-run), plus queueing behind a **global per-repo integrate lock** held by siblings, accounts for the 20–40 min band far more than implementation time does. The single highest-leverage fix is to point the integrate `test_cmd` (and the coder self-verify) at the parallel `-n auto` runner.

## Part 2: Coder Task Latency Analysis

### The mandated coder workflow (source of the fixed costs)

From `src/juggle_task_templates.py` (`TASK_TEMPLATES["coder"]`), every coder task is contractually required to:
1. **TDD cycle** — write failing tests first, confirm RED, implement to GREEN, refactor; commit increments atomically (lines 17–20, 44–47).
2. **Full-suite self-verify ONCE, foreground/blocking** — `uv run pytest -q` or `juggle verify` (lines 22–32). Explicitly *no* subset, *no* background-poll, one green run.
3. **`mike:pre-pr` quality gate** before completion (line 21), which includes a **devil's-advocate adversarial-review pass** (Codex background review) and a harness smoke gate whose summary line must be pasted as evidence (lines 48–52).
4. For non-plan-file tasks, a front-loaded **repro → spec → devil's-advocate → plan** sequence before any code.

Then, out of the agent's hands, `juggle integrate` runs the **whole suite again** inside a global lock.

### Time budget for a typical 25–30 min coder task (rough %)

| Phase | Est. time | % | Notes |
|-------|-----------|---|-------|
| Worktree + trust setup | ~0.25–0.5 min | ~2% | Warm `.venv` symlink, no `uv sync` (refuted tax). |
| Repro → spec → DA → plan (non-plan tasks) | ~2–4 min | ~10% | Front-loaded thinking before code. |
| TDD implementation (RED→GREEN→REFACTOR, atomic commits) | ~6–9 min | ~30% | The actual "writing code" slice — a minority. |
| **Full-suite runs (self-verify + integrate gate, serial ~5.5 min each, 2–3×)** | **~11–16 min** | **~45%** | **Dominant.** `pytest -q` serial; integrate retries once on flake; +1 run on rebase. |
| Integrate global-lock wait (queued behind siblings) | ~0–6 min | ~10% (bursty) | Zero if alone; up to a sibling's full in-lock suite run when 4–5 finish together. |
| pre-pr gate (harness smoke + Codex DA, incl. rate-limit attempt) | ~2–4 min | ~8% | Includes the doctor `--dry-run` smoke + bounded Codex round-trip. |

Net: **~55% of wall-clock is test execution + lock-wait**, only **~30% is implementation.** The 20-min floor and 40-min ceiling are set almost entirely by how many times the serial full suite runs and whether the agent queues behind the integrate lock — not by the difficulty of the diff.

### Recommendations (highest leverage first)

1. **Run the full suite in parallel everywhere it gates — `-n auto`.** Change juggle's `test_cmd` in `~/.juggle/config.json` from `uv run pytest -q` to `uv run pytest -n auto --dist loadgroup -m "not watchdog_proc"` (mirror `Makefile:10`), and update the coder self-verify template (`juggle_task_templates.py:26`) to `juggle verify` backed by the same parallel command. This is the single biggest lever: it cuts the ~5.5-min serial run toward wall-clock ≈ slowest-shard on a multi-core box, and it applies to *both* the self-verify and the in-lock integrate run (which also shortens everyone's lock-wait). **Caveat:** keep it a FULL run (no `slow` deselect — the B2 always-full-suite guard must still pass); `--dist loadgroup` preserves the ordering the `watchdog_proc`/`slow` buckets need.
2. **Shrink the integrate critical section — don't hold the merge lock during the suite.** Today the full suite runs *inside* the global per-repo lock (`juggle_cmd_integrate.py:115`), so one agent's 5.5-min run blocks all siblings. Run the suite on the rebased branch tip *before* acquiring the lock, then acquire the lock only for the fast fetch→(re-verify-if-main-moved)→ff-merge→push. Combined with #1 this collapses the bursty ~0–6 min queue tax. (Requires care: re-check that `main` didn't advance under you after the pre-lock run — a cheap "did origin/main move?" gate that only re-runs the suite on a real change.)
3. **Cut redundant full runs to one authoritative gate.** The coder self-verify and the integrate gate run the *same* full suite minutes apart. Either (a) make the coder inner loop run only the changed-area tests (fast feedback) and reserve the ONE full run for integrate, or (b) have integrate trust a fresh green self-verify tagged with the branch SHA and skip re-running when `main` hasn't moved since. This removes ~5.5 min (one whole serial run, or one parallel run) from the common path without weakening the always-full-suite-at-the-gate guarantee.

Secondary, smaller wins: sequence file-adjacent threads to avoid the B11 rebase-conflict re-runs; pre-flight `juggle doctor` at session start so B10 migration refusals never cost a mid-finalize round-trip.

## Appendix: Open Follow-ups

**Marked open / mitigated-but-not-root-caused in Part 1:**

- **A9a — stale `integrating` topic blocking a cross-topic dep (mitigated by hand).** The underlying class is Defect C in `research/2026-07-01-integrate-machinery-defects.md`: `merged_sha` is recorded fail-soft *before* the push against `origin/main`, so a direct-push integrate can leave `merged_sha` NULL, wedging the topic at `integrating`; `graph reconcile` cannot repair it (it re-derives the same gate). **Follow-up:** give reconcile a git-truth repair path (backfill `merged_sha` when the topic's committed work is already an ancestor of `main`) and/or record `merged_sha` *after* the push against local `main`. Root cause unfixed — tonight was hand-reconciliation only.
- **A9b — terminal threads counting toward the live thread cap (mitigated by raising the cap to 100).** Two residual root causes remain: (i) `failed-exec`/`done` conversation threads should not count against `JUGGLE_MAX_THREADS`; the cap should count only live/in-flight threads. (ii) The cap is an **import-time / daemon-start env constant** inherited from the launching shell — same staleness class as Defect B (`research/2026-07-01-integrate-machinery-defects.md`): a config-authoritative, per-tick-resolved cap would remove the "restart the daemon to change the cap" footgun. **Follow-up:** exclude terminal threads from the cap count; make the cap config-authoritative and re-read per tick.
- **B10 — prod-DB migration refusals in agent context (expected, but frictional).** By-design guard, but it stalls a finalize every time the prod DB is a migration behind. **Follow-up:** pre-flight `juggle doctor` at session start, or gate dispatch on a "migrations current" precondition, so agents never hit `assert_migration_allowed` mid-finalize.
- **B11 — rebase-conflict serialization (expected).** Not a bug; the mitigation is orchestration-side (sequence threads touching the same files; decompose tasks to be file-orthogonal).

**Residual noted by the orchestrator (harmless today, worth cleaning up):**

- **Watchdog "defer to incumbent" path does not exit cleanly after deferring.** In the A3 respawn-reconciliation fix (`7f0b1b8`/`191cfb2`, `juggle_watchdog_respawn`), when a booting watchdog correctly defers to a fresh same-code peer holding the flock, the deferring process's exit path is not clean (it defers but does not tidily terminate). Harmless under current operation (the flock keeps a single authoritative owner regardless), but the losing process should exit deterministically rather than fall through. **Follow-up:** make the defer branch return/`sys.exit(0)` immediately after logging the deferral, with a pin asserting the deferring process terminates.
