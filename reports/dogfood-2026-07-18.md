**Five distinct infrastructure bugs were active simultaneously between 2026-07-09 and 2026-07-13**, affecting any threads created or active in that window:

1. **Label uniqueness gap (D1, 2026-07-09)**: `idx_nodes_live_label` (Migration 54) only enforced uniqueness among `open/running/background` states. A `done` or `failed-exec` conversation had zero DB-level backstop — two rows could share a label with no `IntegrityError`. Proven via direct SQL. Fixed by Migration 75 (`1b90761`). Production evidence: `IntegrityError: UNIQUE constraint failed: nodes.user_label` appearing in spool replay.

2. **Tick dedup hijacking (D2, 2026-07-09)**: `db.create_thread`'s lexical title-dedup guard was reachable from the watchdog tick's dispatch paths. A live ad-hoc thread sharing 2+ significant content words with a tick-minted dispatch title was returned as a "duplicate", bound to the wrong topic, and re-dispatched into — run misattribution and agent-in-flight collision. Reproduced on run 468, thread `def0f69c` (`1b90761`).

3. **Completed agents never decommissioned (Fault 1, 2026-07-13)**: The completed-agent reaper's sole gate was `topic_work_landed(topic)`. A topic stuck in `background` state because its `agent complete` spool event dead-lettered had no backstop — the agent leaked indefinitely. Production dead-letters timestamped 2026-07-12T23:32Z and 2026-07-13T00:39Z (`f389749`, spool events `191c7e17`, `aabd9574`).

4. **Recovery re-dispatch blind to `last_send_task_at` (Fault 2, 2026-07-13)**: `execute_recovery` called `mgr.send_task` directly, stamping only `last_task` on the new agent row — never `last_send_task_at`. The watchdog classifier treats `last_send_task_at IS NULL` as "never dispatched", so a re-dispatched agent that stalled again was permanently misclassified as `awaiting_dispatch` and never recovered a second time (`c17e9a3`).

5. **Late agent-complete reactivating archived threads**: `decide_thread_close` walked a thread to `closed` unconditionally even when already `archived`. `closed` maps to node state `done`, which re-enters the partial `idx_nodes_live_label` index — colliding with whichever conversation the slug wheel had since reallocated the freed slug to. This is the direct source of the `IntegrityError` in D1's production evidence (`01a29d4`).

## Repeated Dispatches / Blockers

**D2 is a repeated-dispatch generator by construction.** Any ad-hoc thread sharing significant words with a tick topic was silently consumed as a "duplicate" and re-dispatched into instead of spawning a new thread. A user seeing their task in-flight would see their ad-hoc thread switch context — the prior work neither lost nor completed, but now carrying a different topic's state. The fix (`skip_dedup=True` at both tick call sites) was landed same-day 2026-07-09, but any threads created before the fix would have been affected.

**Fault 2 is a permanent blocker.** A thread whose first recovery failed would be permanently stuck — the watchdog would classify the re-dispatched agent as `awaiting_dispatch` indefinitely, never triggering a second recovery. There's no self-healing path out: it requires manual intervention or a watchdog restart. This likely affected any threads that hit a stall shortly after being recovered (common pattern when the environment causing the first stall is still present).

**Dead-lettered completions (Fault 1) are an agent leak + blocker.** The leaked agent continues occupying a slot against `JUGGLE_MAX_BACKGROUND_AGENTS`, reducing capacity for new threads. If multiple threads had dead-lettered completions simultaneously, the agent pool would slowly drain until manually killed.

This has now caused two consecutive invalid dogfood reports (2026-07-11 and 2026-07-18). The schedule code has no mechanism to inject DB data into the prompt.

## Suggested Improvements (1–3)

### 1. Embed DB snapshot inline in dogfood prompt
**File: `src/schedules/dogfood.py:45–69, 119–158`**

`_run_headless_research` passes the raw `TASK_PROMPT_TEMPLATE` to `claude -p` with no data attached. The agent has no DB access in headless mode. The fix was identified in commit `4f0ac1e` ("the dogfood prompt must embed the DB snapshot inline") but was never applied to the schedule code.

Concrete change: in `run()` (line 290), after the pre-flight checks, query the DB and format the relevant rows as JSON/markdown, then interpolate the result into the prompt before calling `_run_headless_research`. The `TASK_PROMPT_TEMPLATE` should have a `{db_snapshot}` placeholder and the schedule script should populate it — not the agent.

```python
# in run(), before task_prompt = TASK_PROMPT_TEMPLATE.format(...)
db_snapshot = _extract_db_snapshot(db, since_date)
task_prompt = TASK_PROMPT_TEMPLATE.format(since_date=since_date, db_snapshot=db_snapshot)
```

This eliminates the recurring two-week failure pattern without changing the agent prompt structure.

### 2. Purge dead-letter files after backstop reconciliation
**File: `src/juggle_watchdog_reap_backstop.py` (lines where reconciliation is committed)**

The `dead_letter_matches_agent` timestamp guard (`974705b`) prevents false triggers on retried threads but relies on the dead-letter file never being updated after the original event. As the codebase evolves, this temporal discriminator could drift. The root cause is that reconciled dead-letters are never deleted.

After successfully reconciling a dead-lettered thread (freeing the agent, closing the ledger, filing the action item), the dead-letter spool file for that specific `agent_complete` event should be moved to a `dead-letter-archive/` path or deleted. This eliminates the entire class of "stale dead-letter" false positives, making the timestamp guard unnecessary rather than load-bearing.

---

### 3. Reconcile and sync the migration sequence counter
**File: `src/dbops/migration_seq.py`, `src/dbops/migrations_tail.py`**

The `migration_seq` allocator returned 74 for a new migration when migration 74 was already on disk (`1b90761`). The duplicate-migration-number incident from 2026-07-02 (`CLAUDE.md`) was caused by exactly this desync. The fix was a workaround (re-reserve to 75) — the counter itself was not reconciled.

`migration_seq.py` should have a `verify_seq()` function (callable from `juggle doctor`) that checks: `max(int(f.stem.split('_')[1]) for f in dbops_dir.glob('migration_*.py'))` and asserts the DB-side counter is ≥ that value, raising loudly if not. This makes the desync detectable before it causes another collision, with zero behavioral change in the happy path.
